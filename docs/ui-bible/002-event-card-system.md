# 002. Event Card System

## 1. Цель

Карточка события — единый компонент для отображения события пользователя в
Timeline, поиске, аналитике, истории и будущих AI-объяснениях.

Система карточек должна обеспечивать единое визуальное представление,
предсказуемое поведение и безопасную интерпретацию данных независимо от места
использования. Карточка отвечает за отображение события, но не определяет
медицинский смысл данных и не формирует рекомендации.

## 2. Поддерживаемые типы MVP

- `glucose`;
- `insulin`;
- `nutrition`;
- `activity`;
- `medication`;
- `note`;
- `reminder`;
- `ai_insight`.

Новые типы событий добавляются через расширение типизированного контракта, а не
через локальные исключения в отдельных экранах.

## 3. Общая структура карточки

Карточка события может содержать:

- время;
- иконку типа;
- название события;
- главное значение;
- вторичную информацию;
- контекст события;
- индикатор раскрытия;
- статус;
- источник данных.

Главное значение и название события образуют основной смысловой блок. Остальные
элементы дополняют его и не должны конкурировать с ним по визуальному весу.
Отсутствующие необязательные данные не заменяются пустыми строками или
заглушками.

## 4. Варианты отображения

### `compact`

Используется в Timeline. Показывает время, иконку, название, главное значение и
краткий контекст. Высота и отступы минимальны, но интерактивная область сохраняет
требования доступности.

### `standard`

Используется в поиске и истории. Дополнительно может показывать вторичную
информацию, статус и источник данных.

### `expanded`

Используется для подробностей события. Показывает доступные дополнительные
поля, источник, статус и связанные события. Раскрытие не должно менять или
переинтерпретировать исходные данные.

## 5. Состояния

- `default` — базовое состояние карточки;
- `hover` — визуальная обратная связь при наведении;
- `focus` — видимый фокус клавиатуры;
- `expanded` — отображение дополнительных сведений;
- `selected` — карточка выбрана пользователем;
- `loading` — данные загружаются, структура карточки сохраняется;
- `error` — данные недоступны или не могут быть отображены;
- `disabled` — взаимодействие временно недоступно.

Состояния не должны передаваться только цветом. `loading`, `error` и `disabled`
должны иметь понятное текстовое или семантическое представление.

## 6. Правила контента

- главное значение читается первым;
- единицы измерения всегда отображаются;
- технические термины не показываются пользователю;
- причинно-следственная связь не утверждается;
- медицинские рекомендации отсутствуют.

Контекст описывает последовательность или условия события нейтральным языком:
например, «Перед завтраком», «После прогулки» или «Через 2 часа». Контекст не
должен интерпретировать влияние одного события на другое.

## 7. Типовые данные для каждого типа события

### Glucose

- значение;
- единица;
- контекст измерения;
- источник.

### Insulin

- препарат;
- доза;
- тип инсулина;
- контекст.

### Nutrition

- название приёма пищи;
- углеводы;
- ХЕ;
- контекст.

### Activity

- вид активности;
- длительность;
- интенсивность.

### Medication

- название;
- доза;
- статус приёма.

### Note

- краткий текст;
- вложения при наличии.

### Reminder

- название;
- статус выполнения;
- плановое время.

### AI Insight

- краткое нейтральное объяснение;
- ссылка на связанные события;
- без диагноза и назначения лечения.

AI Insight должен быть явно обозначен как автоматически сформированное
объяснение и визуально отличаться от зафиксированного пользователем события, не
нарушая общую структуру карточки.

## 8. Accessibility

- полная клавиатурная навигация;
- видимый `focus`;
- информативный `aria-label` для элементов управления;
- достаточный контраст текста, иконок и состояний;
- раскрытие через `Enter` и `Space`;
- минимальная область нажатия 44×44 px.

Порядок фокуса соответствует визуальному порядку. Декоративные иконки скрываются
от assistive technologies. Состояние раскрытия передаётся через
`aria-expanded`, а связь с областью подробностей — через `aria-controls`.

## 9. Адаптивность

### Desktop

Карточка использует доступную ширину контейнера. Вторичная информация и источник
могут располагаться в отдельной зоне, если это не ухудшает порядок чтения.

### Tablet

Карточка сохраняет основной горизонтальный ритм, а вторичные данные при
необходимости переносятся на следующую строку.

### Mobile

Главное значение остаётся визуальным приоритетом. Вторичная информация и
контекст переносятся без обрезания критичных данных. Интерактивные элементы
остаются доступными для касания.

На всех размерах экрана горизонтальная прокрутка отсутствует.

## 10. Definition of Done

- определён единый API компонента;
- используется строгая типизация без `any`;
- поддерживаются все MVP-типы;
- состояния документированы;
- компонент пригоден для повторного использования;
- тесты предусмотрены.

Тестовая стратегия должна предусматривать unit-тесты вариантов и состояний,
проверки доступности, визуальные проверки ключевых представлений и адаптивное
поведение на поддерживаемых размерах экрана.
